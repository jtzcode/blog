在上篇文章中，我们讨论了 Build 工具并且提到了依赖管理，本文将深入探讨依赖管理的概念、挑战以及常见的策略。

依赖管理的挑战在于，随着项目的演进，外部依赖的版本会不断变化。有些变化会导致破坏性改动（Breaking Changes），从而影响项目的稳定性和功能；有些变化则会导致版本冲突，无法满足所有依赖的版本要求。

这就是依赖管理需要解决的问题，依赖管理本质上管理的是版本的更新。接下来我们从静态模型、Live at Head 模型和语义版本（SemVer）三个方面来探讨依赖管理。

## 静态模型

静态模型假设外部依赖无需变化。

这是一种简单的、高效的管理模型，适用于项目开始阶段，虽说简单粗暴，但不是全无用武之地。

依赖管理的复杂性随着项目的演化才会体现出来，没有长的时间尺度，也体现不了依赖需要添加、更新的必要性：如添加新特性、修复潜在功能问题、修复安全问题等。

这里说的不变，是指对依赖变化的需求不变，而不是依赖本身不变。我们通常无法控制外部依赖（如来自开源社区）的变化，但是多数变化可能不是你需要的。

如果依赖仅仅优化了性能、新增了功能，对你的项目可以锦上添花，但不是必须的。

如果依赖修复了严重安全漏洞，对你的项目则是必要的；毕竟，出了安全事故，可能损失巨大。

因此，不要预先假设复杂性和需求，简单的模型很多时候是够用的。

## Live at Head 模型

Live at Head 策略也比较简单直接，并且在另一个极端：始终保持每个依赖在最新版本。

虽然回避了利用语义版本进行管理的复杂性，但是最终还是要面对依赖之间冲突导致的实际问题。

比如，一个依赖接口的破坏性改动（Breaking Changes）会影响所有该接口的客户端代码。

如果是完全开源的生态系统，问题也不大。开源社区通常有完善的 CI 和测试系统，高效保证代码本身的正确性。

同时，开源社区注重声誉，每个软件在发布新版本前，都要考虑对下游用户的影响。下游的开源用户也会通过自身的测试，很快发现问题并提供反馈给上游开发者。

如果是在完全封闭的项目中，问题也不难解决。这类项目的上下游代码都是由同一团队或者组织负责开发和维护，对于某个依赖的使用场景了如指掌，因而可以使用充分的自动化测试和 CI 系统，覆盖所有可能的使用场景，进而及早暴露版本更新带来的问题。

问题暴露后就可以决策：是坚持更新版本，并通知下游代码做相应调整；还是回退版本，采取更为保守的更新策略。

比较难处理的是内部项目采用了部分开源实现。

开源部分的开发者不能假设，其代码的使用者有完善的自动化测试，以尽早发现依赖更新带来的问题。

闭源部分的开发者也没有动力去为开源代码发现问题并提供反馈。因此，依赖版本更新通常意味着项目构建失败，甚至有些问题在运行时才会暴露。

作为应对策略，很多团队会采用静态模型，保持构建的稳定。久而久之，当有不得采取的更新时（例如安全更新，或者旧版本停止支持），问题反而会积累得更多而积重难返。

## 语义版本 （Sementic Version）

如果你使用过一种依赖或者包管理器，则对语义版本（以下称「SemVer」）[1]并不会陌生。

语义版本提供了一种声明版本更新语义的方式，依赖的使用者可以据此判断某个版本可能引入的影响。

简单回顾一下，一个 SemVer 版本号由三部分组成：主版本号（Major）、副版本号（Minor）、补丁版本号（Patch），格式为 `MAJOR.MINOR.PATCH`，分别对应破坏性改动、兼容性改动和问题修复（补丁）改动。

采用 SemVer 进行依赖管理，本质上是一个 SAT （Satifiability）约束求解问题[2]。

SAT 问题简单来说是：
> 给定一系列布尔约束，求是否存在一种变量赋值，让所有约束都同时为真？

例如：
```css
(A or B) and (not A or C) and ...
```

求解这类问题的算法称为 SAT Solver，目前主流的包和依赖管理器底层都采用这种方法解析依赖。

比如，一个项目需要依赖库 A 和 C，二者同时依赖库 B，并满足版本要求：
- A 需要 B 的版本 >= 1.0.0 且 < 2.0.0
- C 需要 B 的版本 >= 1.5.0

假设 B 有三个版本可选：1.0.0、1.5.0 和 2.0.0，可以对应三条布尔约束：
- B1 -> B == 1.0.0
- B2 -> B == 1.5.0
- B3 -> B == 2.0.0

要满足 A 和 C 的依赖要求，可以转换为以下布尔表达式：
```
(not B3) and (B2 or B1) and (B1 xor B2 xor B3)
```
即，不能使用 B3，且从 B1 和 B2 中选择，且只能选择一个版本。

SAT solver 会尝试求解这个表达式，找出满足所有约束的版本组合。

上面这个问题很简单，但实际的项目依赖树可能很复杂，约束的求解也变得困难，甚至没有解。此时依赖管理器通常会报版本冲突的错误，提示开发者手动干预。

从上面求解过程也能看出，约束的定义需要考虑每个依赖库的支持的所有版本的情况，因此假设有个 n 个依赖，每个依赖有 m 种版本，则总的组合数是 m^n。

随着依赖数量和版本数量的增加，求解复杂度会迅速上升。事实上，这个问题已被证明是 NP-Complete 问题。

SemVer 的一个限制是，它十分依赖开发者对版本兼容性声明的准确性，而这个声明往往是开发者自己估计的。

SAT solver 依赖严格的布尔约束，但是在兼容性的声明中，这个布尔值不能保证真实性。这会导致两方面问题：

- 过度约束问题：多数项目不会接受主版本更新， 默认将其视为 breaking changes，会对已有功能产生影响。

但事实上，很多主版本改动虽然变更了接口，但并不是项目所必需的，因此升级后并不会产生影响，反而无法获得有用的新特性。

- 过度承诺问题：很多时候，SemVer 的版本语义并不真实反馈变更的影响。例如，尽管 patch 类改动仅变更内部实现，而不影响接口使用，但开发者并不知晓哪些内部实现已经被使用者依赖（顺序、延时、特定文件等），这就又体现了 Hyrum 定律[4]。

因此，Breaking Change 这个词的定义就不那么精确：有些改动是理论上破坏性的，实际则是安全的，如删除一个无用的 API。

而有些改动理论上是安全的，实际则是破坏性的。这样的例子在使用开源库时会经常遇到，一个副版本更新，比如从 5.97 到 5.98，却引入了 bug。是否是破坏性改动，完全由下游用户如何使用来决定。

虽然多数开发者倾向于「不」升级主版本，引入 breaking changes，然而另一些开发者可能会主动寻求主版本升级，因为所谓不破不立，抛弃就代码，重新设计和实现有时会带来更好的结果。

就看是否值得如此：你是看中更健壮的实现、更强大的功能，还是倾向于维持现状但需要忍受偶尔的小问题。本来选择权在用户，但是 SemVer 的机制可能会导致事与愿违。

SemVer 的限制本质上是，将软件的变化的影响压缩到一个版本号类型中，而版本号往往不能忠实反映变化的真实影响。

比如，一个软件库 A 声称，其依赖库 B的版本要满足 v >= 2.1，这是否意味着 B 的 2.1 及其以上版本就能保证 A 正常工作？这只是理想情况，事实上即便采取最小版本选取策略（Minimum Version Selection），即指定 v == 2.1，也无法给出这样的保证。

因为既然 A 的作者给出这样的声明，那他至少在 2.1 的版本上测试通过，但这只针对了作者指定的场景，并不能说明在所有场景下，这样的版本组合都是正常的。

总结起来，SemVer 在什么时候有用？

1. 依赖提供者判断准确。这是 SemVer 最大的问题：它假设维护者能 100% 正确判断对所有用户是否兼容，这是不可能的。
2. 依赖足够细粒度（fine-grained）。依赖的API 设计足够细粒度，可以避免很多过度约束的问题。
3. 所有 API 的使用方式都在预期范围内。Hyrum 定律决定了这个也很难实现。

鉴于 SemVer的局限性，有些组织会采取其他的依赖管理策略，如 Google 的单一版本策略（One-Version）[3]。

单一版本要求整个代码库中每个依赖只能有一个版本，避免了版本冲突的问题。

如果在引入新的依赖库时发现版本冲突，则需要直接解决掉。首先，看是否可以找到兼容的版本；如果不行，就需要选取其中一个版本，对于冲突的使用端的代码作出相应修改，以适应这个版本。

这相当于在引入某版本时把问题解决掉，方案就是保持版本的唯一性，而不是等到未来某个时刻，产生冲突时才暴露问题。

值得一提的是，Google采用这类方案的一个原因是，其代码库是一个巨大的 monorepo，所有代码都在一个版本控制系统中进行管理，因而可以方便地对所有代码进行全局修改，以适应依赖版本的变更。并不是所有的组织都适合采用这种策略。

## 结语

语义版本是依赖管理的常用方法，不过面对具体的、复杂的项目时，其依然有不可忽视的局限性。采用单一版本策略虽然可以规避版本冲突的问题，但并不一定适合所有代码仓库使用。
