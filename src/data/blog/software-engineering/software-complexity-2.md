在上一篇文章中，我们考察了复杂性的几种度量方法。如果你仔细辨别不难发现，这些度量其实都在关注**事物本身的特点**；而我们采用的软件复杂性，则是从「人」这个角度理解的，强调人（开发者）对软件系统的认知以及与之对应的行为。

你这边多思考几步，使用者就会少一些负担和疑惑，给其他开发者造成的不便，最终一定以某种方式体现到软件质量上（如技术决策失误，引入未知的bug等），甚至反嗜自身。

这就是为什么软件复杂性的三个维度都是从软件开发和协助的角度说的。

如果关注复杂性成为团队的习惯和规范，软件质量和整体的开发效率就会大幅提高。而事实上这样的团队并不多见，原因有二：

1. 开发者的总是瞄准局部的目标，以快速完成任务为目的。
2. 开发者并没有意识到复杂性引入的问题，配套的培训和**Code Review流程形同虚设**。

好的软件设计虽然降低了阅读者和使用者的认知负载，却可能增加开发者本身的认知负载，这一点要注意区分；有些人苦思冥想也不得其解，有些人则轻车熟路很快就给出好的方案。因此，对于新手来说，只会停留在较差的设计上而不自知，复杂性引入就在所难免了。

我们依然以《软件设计哲学》[^1]为本，学习降低软件复杂性的思路和方法。

## 战术性编程 vs 战略性编程
首先我们抬高视角审视一下编程的目的。如果开发者仅仅以完成任务为目的，这就是「战术性编程」（Tactical Programming），它的主要关注点是工作的代码（Working Code）；与之对应的是「战略性编程」(Strategic Programming)，主要关注点是好的设计（Great Design）；

二者并不冲突，只不过由于各种现实因素，战略性编程的意义被忽略或者无视。而这是降低软件复杂性的根本思想，即**永远追求和保持好的设计，在此基础上完成功能迭代**。

“战略性”的意义还体现在，很多功能的实现如果基于好的设计，可以完成的更加高效，并有更高的质量。扩展性的代码可以完成的水到渠成，而无需从头设计。

什么时候开始战略性编程都不晚。即使你的代码库的问题已经积重难返，小步改良和重构也是不错的开始，至少在将来某个需求实现上可以带来收益，而后续的收益又会带来新的收益。

## 深模块与信息隐藏
现代软件开发离不开模块化设计的思想，既然拆分了模块，就必然伴随着信息的**隐藏和暴露**。信息隐藏可以降低模块使用的认知负载，信息暴露则提供必要的接口，这都是正常现象。

有问题的是「信息泄露」。信息泄露实际是违反了高内聚低耦合的原则：没有把相关功能放到一起，导致模块之间耦合严重，且每个模块都有信息泄露。它的一个标志是：在多个模块同时出现相同的信息。

好的模块是所谓的「深模块」（Deep Modules）：提供强大丰富的功能，却只暴露简洁的接口。

很多接口的参数就暴露太多内部实现，使用者需要了解每个参数的含义，是否可选，甚至还需要理解接口的实现，才知道如何传递参数，这就不是好的模块设计，即所谓的「浅模块」（Shallow Modules）

# Shallow module: user must understand too much

resize_image(img, 300, 200, "bilinear", True, False)

另一种导致信息的泄露的原因是「时序分解」（Temporal Decomposition），即我们**习惯于按照时间发生的顺序来定义和拆分模块**。

例如，应用程序需要读取特定格式文件，处理文件内容，然后写入输出文件。时序分解的思路是，读取文件一个类，处理文件一个类，输出结果一个类；显然，如何读取和写入文件都需要文件格式和编码的信息，这部分信息是需要共享的，不能出现在多个模块单元中，造成信息泄露。因此，读写文件的逻辑应该在一个类中。

当然，按照时序来做业务流程分析没有问题，但不要过早落实到代码设计，要分析每个步骤业务背后的技术特点，综合考虑设计。即使形成了基于时序的设计，只要头脑中有避免信息泄露的意识，也可以逐步重构改善。

说到信息隐藏这一点，我联想到日常的一种行为：读源码。很多时候我们读源码是为了了解具体实现，以便发现问题或者优化方案，那么一个开放问题是：如果模块或者组件的调用者需要阅读源码后才能高效的使用，那么是不是有些必要信息没有暴露，即信息隐藏过度了？

## 一般化与特殊化

软件模块设计有一般化和特殊化的权衡。简单来说，一般化是指将相似的功能抽象出来，形成通用的模块（类、方法、接口等），而特殊化是指针对特定需求的定制化实现。

一般来说，写**更通用的代码**会降低复杂性，接口定义也更明晰。

然而，特殊化实现也不可避免，通常的做法是：**将特殊化代码移动至其他层次**，可能是上移（如到UI表示层的逻辑），也可以是下移（如系统驱动程序的接口）；这取决于**变化的来源和抽象发生的层次**，可以从「需求方」和「实现方」的角度理解。

**需求方**：不管底层的实现如何变（如各种设备驱动程序），我都需要以统一的接口实现上层应用程序（如系统应用）。这是将特殊化代码下移。

**实现方**：不管上层的 UI 有怎样的操作（如文本编辑器的操作），最终都是调用我这里抽象出的接口。这是将特殊化代码上移。

总之，只要这些特殊化的代码在统一层次，就有利于模块化开发，有利于降低复杂性。

## 警惕 Pass-Through

Pass-Through是指方法或者变量的透传，比如某个函数参数跟随一层层调用传递下去，在中间层次很少使用。

这种做法增加了类的接口复杂度，又没有提供额外功能。这通常意味着：**层次之间的职责划分不清晰**。同时也增加了类之间的依赖。

在设计模式中，「装饰器」（Decorator）类就会产生许多 pass-through 方法，而且会定义大量的 「Shallow Class」。

```java
import java.io.*;
public class DecoratorExample {
    public static void main(String[] args) throws IOException {
        String text = "Hello, Decorator!";
        byte[] bytes = text.getBytes();
        // 原始输入流
        InputStream byteArrayInputStream = new ByteArrayInputStream(bytes);
        // 装饰器：BufferedInputStream
        InputStream bufferedInputStream = new BufferedInputStream(byteArrayInputStream);
        // BufferedInputStream 定义了很多 pass-through 方法
        // 例如 read(), available(), close() 都只是调用底层 InputStream
        int data;
        while ((data = bufferedInputStream.read()) != -1) {
            System.out.print((char) data);
        }
        bufferedInputStream.close();
    }
}

```
在这个实现中，大部分方法最终调用内部的 `InputStream` 对象的方法（pass-through）；并且，这种设计使类变浅（shallow class），用户看到的接口很多，但大多数只是转发到底层实现（如read、skip 和 close 等），并没有提供太多额外功能。

因此，考虑使用装饰器模式时，要多问几个问题。装饰器更类似于一种补救措施，而不是主动设计手段。从降低复杂性的角度说，不是好的选择。

当然，装饰器模式也有其优势，需要权衡利弊，比如：
1. 遵循开闭原则：不用修改原类，就可以增强功能。这在无法修改源代码或需要保证核心逻辑独立的场景非常重要。

2. 组合优于继承：如果只用继承，为了支持组合场景（如有日志、有缓存、有安全验证的组合），可能需要很多派生类（类爆炸）。装饰器虽然增加了类数目，但它们可以任意组合，避免了**继承树爆炸**。

3. 可渐进增强：你可以先有一个基本功能的对象，再慢慢添加功能，甚至可以根据配置文件或用户需求，灵活地叠加装饰器。

Pass-Through 变量也是个问题。

变量作为参数逐级传递，一旦如果有增加或修改，你需要更改多个接口（变更放大）。使用这类变量的出发点是，底层接口实现依赖高层接口的某个变量，但又无法直接获得，则逐层传递（或者声明于全局对象，也不是个好主意）。

把传递的变量作为一个 context 对象的多个属性，可以减少传递变量的数量，但 context 对象本身依然是透传的。因此，也可以将 context 对象封装成系统全局的对象，并通过特定方法获取访问。这样每一层方法只在需要的时候可以方便拿到对象的引用。

但注意，context 对象依然有全局变量的缺点，比如你经常要耗费精力调试，到底是哪一层的方法改变了 context 对象的某个属性，这就是晦涩的引入。

## 实现的分离与合并

还有一个比较具体的问题，我们在实现一个方法时，何时需要将部分逻辑抽取出来作为子方法，何时需要避免拆分而保持原方法的完整性？这里面也涉及复杂性的考量。

一些重构思想认为，长方法是一种代码的「坏味道」，尽量保持方法的简洁。而从复杂性的角度说，长方法并非总是坏代码。不抽取单独的方法，就省去了来回跳转带来的认知负载。因此只要：

1. 方法接口明确清晰
2. 方法体的代码块易读易懂

就可以保留长方法的写法。好的代码原则和设计思想不能生搬硬套，要注意最初的目的是什么：**为什么代码会晦涩难懂，仅仅是因为方法很长吗**？

抽取子方法的原则是：**抽取子方法后应当不影响父方法的理解，理解子方法也无需依赖父方法后续实现**。按这样的原则抽取的方法，通常是比较**通用的代码**。

不要纠结于于方法的长度本身（例如某些代码扫描工具规则），方法的**深度**更重要，即它是不是有丰富的功能和简明的接口，正如作者所说：

> “Depth is more important than length: first make functions deep, then try to make them short enough to be easily read. Don’t sacrifice depth for length.

## AI 能做什么
面对软件复杂性，AI 工具能帮我们做什么？我觉得至少有两个方向：
- 面对复杂性很高的遗留代码，AI 工具有助于理解代码的结构，分析依赖，识别问题，提出重构建议，从而减少认知成本和维护成本。目前很多 AI IDE 工具的都具备 Agent 能力， 让 Agent 以 task 的形式完成分析和重构任务，我已经在尝试了。
- 面对新的需求，AI 工具可以帮助我们设计出有利于降低复杂性的软件架构和代码实现。如果语言模型尚不具备这种能力，则是一个模型训练和微调方向。事实上，目前的模型已经能给出比较好的代码设计建议，但缺乏复杂性分析的维度。

最后，再次推荐《软件设计的哲学》这本书，这两篇文章不能尽数书中的精彩之处，建议亲自阅读。软件和架构设计确实体现了”哲学“和”辩证“的一面，设计原则和最佳实践都有各自的场景和限制，不能一概而论，我认为这是优秀软件工程师和架构师的基本思维框架。这本书中多个章节的结尾都会有个标题：Taking it too far，作者在时刻提醒你，**不要在某个原则和建议上走的太远**。
