上一篇文章谈到软件工程所考虑的基本问题，其中构建可持续的软件系统和产品是核心目标之一，而实现可持续性的关键是可维护性，这两个概念感觉没有理解透彻。这篇文章首先辨析一下二者的区别和联系，接下来从统一代码风格、Code Review 实践、团队协作方式等几个方面，谈谈流程对软件工程的重要意义。

## 可维护性 vs 可持续性

可维护性（Maintainability）：让软件在生命周期内容易修改、修复和扩展。

衡量的指标有：代码可读性、模块化程度、回归测试成本、文档质量等。关注的是中短期的日常开发和维护。关键目标是降低未来修改的成本和风险。

可持续性（Sustainability）：让软件在长期（甚至十年以上）保持健康、可演化和经济可行。

衡量的指标有：架构演进、技术债积累、知识传承和维护成本等。关注的是长期的、战略性层面的维护。关键目标是让软件不会因为技术腐化或组织问题而“不可救药”，从而被迫重写或废弃。

从定义可以看出，实现可维护性是实现可持续性的一个重要方面，没有维护就没有持续可言。

可持续性应该是软件系统和产品追求的基本目的（没有这个目的，其他的无从谈起）：想想你亲身参与的项目代码，哪些是运行了十年左右甚至更久的长期项目。

它们是否还能轻易的添加和修改功能？是否还可以做架构演进？是否有完善的文档？是否要花费大量时间来回归测试？你和团队是否有推倒重来的冲动？如果很多问题的答案都是负面的，那就是不可持续的典型了。


## 统一代码风格
在团队或者公司范围内采用统一代码风格，是一个常见的开发流程，但实践效果往往事与愿违。究其原因是对保持统一代码风格的必要性认识不够，所谓无法做到「知行合一」，根本原因在于没有「真知」。

代码风格规则的制定不是想当然的，或者从其他知名企业借鉴一份了事，而是要服务于特定目标，由这个目标驱动，拣选需要的规则。最终的目的应该是收获可维护、可持续的代码。

对于技术背景复杂的团队来说，如果没有统一的代码风格规则，代码的可读性会受到影响，不易管理和维护，团队整体协作效率也会下降。

选择风格的规则多种考虑，这里强调两点:

- 考虑可读性
- 考虑一致性


### 可读性
一段代码被读到的次数要远大于被写入的次数，因此在可读性上投入是值得的。

可读性不仅仅是指让读者可以看懂代码的逻辑，还可以帮助代码的使用者规避使用上的误区。

Google有一个C++指针的例子，可以很好地说明：
```cpp
// Function that takes a Foo* and may or may not assume ownership of
// the passed pointer.
void TakeFoo(Foo* arg);

// Calls to the function don’t tell the reader anything about what to
// expect with regard to ownership after the function returns.
Foo* my_foo(NewFoo());
TakeFoo(my_foo);

// Function that takes a std::unique_ptr<Foo>.
void TakeFoo(std::unique_ptr<Foo> arg);

// Any call to the function explicitly shows that ownership is
// yielded and the unique_ptr cannot be used after the function
// returns.
std::unique_ptr<Foo> my_foo(FooFactory());
TakeFoo(std::move(my_foo));
```
从代码和注释可以看出，使用普通指针的版本，在`my_foo`指针传递完成函数调用后，并不知道该如何处理；而使用智能指针的版本更清晰地表达了所有权的转移。因为`TakeFoo`方法的调用者在传参时，需要显示指定`std::move`，表明所有权的转移，这样可以避免误用和潜在的内存泄漏问题。

从这个例子可以看出，所谓`代码风格`，并不一定是语法层面的，而是更广义的设计和实现层面的。它可以帮助代码的使用者更清晰地理解代码的设计意图。


### 一致性
一致性的好处可以概括为：
> Consistency enables scaling. 

这句话可以从两个角度理解。

工具角度：如果代码的风格、结构在团队之间保持一致，那么就可以设计更为通用的开发和维护工具，实现规模化应用。

例如，一个工具可以为源代码文件移除不需要的`import`，并按照字母升序排序；如果所有文件都采用一致的风格要求（如 import 的位置、排序规则），那么工具就可以统一处理；否则，工具就需要很多特殊处理去兼容，或者干脆维护多个工具，就丧失了规模化带来的效率优势。

人的角度：团队规模扩大后，经常会有人员流动，如新员工加入、跨项目开发、跨团队支持等。一致的代码风格和技术栈，让知识分享和传递的效率更高。

联想到为什么《人月神话》中强调，进度落后时增员于事无补？一个重要原因就是新人要熟悉已有的技术、设计和代码，这个过程的耗时不可忽视。而一致性可以减少这部分开销，有利于团队和项目的规模化。

因此，保持代码风格的一致并不是让你「显得」专业，而是切实可以提高团队研发效率。

对于代码风格规则，自动化检查和格式化工具很重要。这是因为：

1. 不是每个人都记得所有的规则；
2. 规则也会随着语言和技术的发展演化更新，不是所有人都能意识到有更新；
3. 每次都考虑风格规则或者去查询文档都是低效做法；

只要保证自动化的工具及时同步最新的规则，那么所有人都可以正确地、强制化地应用规则。

另外，每个工程师可能以不同的角度解读某个规则，导致最终实现的不一致，这个也可以通过工具来避免。这也是规模化的体现，一个团队开发和应用的工具，可以成为标准惠及整个组织。

## Code Review 实践
Code Review 与前面说的统一代码风格有类似的问题：大家都认可它的必要性，但实践起来却难以推进或者大打折扣。

虽然这个话题是老生常谈，但我还是想总结分享几个实践建议，如果您理解透彻并实践，一定会对团队有帮助。

轻量级的、高效的 Code Review 流程可以帮助我们节省测试、调试、回归等步骤的时间。这里的前提就是“轻量级”和“高效”，较重的、无效的 Code Review 流程是不可持续的。

轻量的 Code Review 要求每次提交评审的代码仅包含较小的改动，这至少有几个优点：

1. 提高效率，让评审者有足够的时间来专门进行评审。很多时候，代码 Owner 抗拒评审任务，就是代码的改动过于复杂，占用他们宝贵的的认知带宽和注意力。
2. Bug 的定位更高效，在一个完整 feature 的代码改动中需找引入 bug 的代码，其难度显然更大。

一个可以参考的代码改动规模是：少于 200 行代码或者评审者能在 1 天之内给出第一次反馈。

“高效”意味着，流程要达到预期目的。正确性是最基本的目标，除此之外还可以是：

> A code review is often the first test of whether a given change is understandable to a broader audience.

这句话点出了 Code Review 流程的一个重要作用：保证代码可读性。代码的正确性有测试可以保证，可读性却容易被忽视。

再厉害的开发者，他对于写的代码也仅仅具有个人视角，他的代码会被很多人读到，所有的来自代码读者的反馈才是可读性的真实度量。

让所有看到代码的人都提出反馈显然不现实，code review 就提供了一个窗口，让一段代码获得更多的视角。

一句评论可能无足重轻，接不接受均可，但随着时间推移，当更多的人提出类似质疑时，当初的第一句评论显得尤为关键，而当时去更改代码是成本最低的时刻。因此，要重视评审中的每一个建议。

Code Review 还能提供心理上的价值，我认为也比较关键。

首先，多数人是从心理上是不愿意别人针对自己的工作，提出比较直白的批评的。Code Review 流程提供了一个缓冲机制，它是一个预设的、中立的流程，为批评提供了一个安全的容器。

当审查者提出修改意见时，其背后的潜台词是：“根据我们团队的审查流程和标准，这段代码可以这样改进”，而不是“我认为你这个人写得不好”。这极大地降低了批评的攻击性，使作者更容易以建设性的心态接受反馈。

另外，Code Review 流程还能起到验证和认可的作用。

有些工程师可能对自己的代码在技术上、业务上是否有问题不太自信，Code Review 可以让你快速看到结果，验证自己的理解，很多时候其实是自己“想多了”。

通过与评审者的多轮交流，既获得了领域和技术知识，也获得了心理上的认可。这也是很关键的。

Code Review 参与者的专业性即是责任。

对于代码评审者来说，你的每次通过都关乎整个团队或者产品的代码质量，不能轻易下结论。很多公司的规则都是，有一位评审者通过即可，因此评审者的意见更显重要。

对于代码提交者来说也是一样，不能为了进代码而进代码，要在评审者介入之前，就把自己能考虑到的、涉及代码正确性、可读性等方面的问题都尽量解决，而不是所有的压力都丢给评审者一方。

Code Review 对于双方都是学习过程。

代码评审不是提交者单方面学习的机会，因为代码提交者也可能提出优秀的方案，只要证明自己的方案与评审者的建议等效或者更优，评审者就需要通过，进而从中学到了新的知识。

在推广代码评审流程并形成规则之前，团队应该真正同步并消化以上这些认知，把问题和顾虑解释清楚并给出方案；否则就会出现说一套做一套的现象，最终让流程形同虚设。

## 工作模式：成员如何协作
除了各类流程，工作模式也是软件工程中不可回避的话题，即团队成员如何组织、沟通和协作？

我们首先回到 Brooks 定律：Brooks 在《人月神话》里指出，单纯增加团队人员，并不能减少任务完成时间，因为人员之间的沟通成本会随着数量非线性增长。

他这里的任务指的是那些无法分解的任务，团队成员之间为了完成任务，必须有效沟通，通力合作，不能各自为战，互相之间有较强依赖。因此，沟通时间成本不可忽视。

由此想到外包公司的逻辑：人员规模通常很大，为了完成客户的开发任务而招兵买马。

外包的任务通常比较细化了，在拆分粒度和独立性上可能比较高了，可以减少开发者之间的沟通，因此人海战术可能有效。

但上面是比较理想的情况，总会有更复杂的软件系统，即使外包出去后也无法有效拆分和细化。

此时如果不注重沟通和协作，问题就出现了：一来任务之间的依赖性导致进度会严重变慢，二来开发者之间的信息差导致质量也大打折扣。

这可能就是外包工作为什么加班频繁而口碑又不受认可的原因之一。

这个定律在特定场景下确实很有意义，也被很多软件团队的经验所证实，但也不能生搬硬套。

比如，《大教堂与集市》一书中总结了开源社区的成功经验。

开源社区也经常有大型软件系统产出，比如 Linux 操作系统。这些软件和系统也不停地有新鲜血液加入贡献者的行列，并没有妨碍质量的稳定和可持续的成功。

因此，并不是团队规模增加就必定导致软件项目失败。

这是因为 Brooks 定律有几个前提：

首先有明确的 deadline，有 deadline 就有进度的规划，这是项目成败的一个指标；而开源项目很多没有明确的规划，新成员的加入并不是为了完成进度指标。

第二，Brooks 所讨论的软件团队内部的合作和沟通是非常紧密的，理论上每两个人之间都需要有沟通。因此沟通成本会随着人员数量非线性增长，但这在实际的团队中是非常少见的。

大型开源软件和系统的模块化程度通常很高，只有少数核心维护者负责掌控架构和代码合入，大部分开发者通常只专注于若干子模块，因此沟通成本大大降低。

另外，Brooks 所讨论的团队中，增加人员需要 mentor指导、统一规范和共享项目知识，这些都要不可忽略的额外成本。

加入开源项目的贡献者，默认需要对项目的整体架构和技术细节有足够的认知，在成为真正的贡献者之前，已有足够时间的自我培训，这些知识都体现在代码提交中。

因此对于整个项目来说，并没有显著增加培训和知识共享的成本。

## 概念完整性
那么在人员确定的情况下，成员之间该如何分工？不同的团队和个人负责软件系统不同的子模块，还是统一进行架构设计，然后分工实现？

《人月神话》的建议是采用“外科医生-副手”模式，即强调团队中一到两个人了解所有的设计和全部代码，其他人只是在各方面提供支持。

这样保证了关键人物的“概念完整性”，这是一个很重要的思想。

与之相对的是，把软件系统或产品拆分为多个任务并分配出去的做法，每个小的团队都只有自己认领任务的视角，考虑协作和交互的问题时，难免有失偏颇。这既增加了沟通成本，又难以达成一致，最终做出不合理的决策。

我就经历过Web应用项目的前后端团队的争执，某个接口的数据前端同事认为应该由后端实现计算得到，而后端同事认为，应当由前端计算好后直接提供。各自的出发点就是：不想更改已有的设计和实现。

这类问题往往没有固定答案，需要的是特定问题场景下的全局视角，即“概念的完整性”，给出合理的方案。

在实际工作中，承担“概念完整性”的成员往往是架构师之类的角色，负责整体的系统设计、决策和取舍，以及初步实现。

然而，当系统开始真正开发时，又难免按照技术栈来分配任务。因此，让所有开发团队深入理解整体设计是十分必要的。

注意，重要的是领会“概念完整性”的思想，不要拘泥于职责的划分。

另外，Brooks 还通过观察提出一个反直觉的观点：明确的外部架构设计不仅不会限制团队的创造力，反而会提升实现效率并激发创新。

当系统架构（即顶层设计，如模块划分、接口规范、技术约束）由外部团队（如架构师或设计小组）预先定义时，实施团队的创造力反而会被激活。

原因是，架构的清晰性为团队提供了明确的边界和约束，使他们无需纠结于基础决策（如技术选型、模块划分），而是专注于具体实现中的创新问题。

其中的一个隐含逻辑是：创新需要“有限制的自由”——清晰的边界反而让团队更容易找到突破点。

布鲁克斯的论点在大规模、需求稳定的项目（如操作系统、基础设施）中极具价值，但在快速迭代或需求模糊的场景（如互联网产品、AI实验）中需灵活调整。

架构师和架构团队的存在可以避免技术决策上的“过度民主化”，即因为不能达成一致，导致迟迟不能决策开始实现。

我之前的一家公司的技术团队有专门的架构组，目的就是为研发团队的技术提供兜底和拍板。当有争论时，最终由架构组形成一致意见并尽快实施。

这是一个好的实践。遗憾的是，很多时候架构组并没有起到权威的作用。
