# 一、我们真的理解“模块化”吗？

可以从一个很有意思的矛盾开始。

早在 1971 年，模块化已经是软件工程中的共识。Parnas 在文章开头甚至调侃，如果程序员会唱赞美诗，那么“模块化程序设计”一定是最流行的赞美对象之一。

然而，当时那些最典型的大型软件失败案例，本身往往已经是“高度模块化”的系统。

所以问题并不在于：

> 系统有没有被拆成模块。

真正的问题是：

> **我们依据什么标准，把系统拆成这些模块？**

Parnas 认为，模块化能带来三种重要收益：

* 不同团队能够相对独立地开发；
* 一个局部变化尽量不影响其他部分；
* 人可以一次理解一个模块，而不用理解整个系统。

但只有正确的模块划分，才能真正得到这些收益。

这里可以顺势提出全文的核心观点：

> **模块化真正要管理的，并不是代码数量，而是知识、变化和依赖在系统中的传播。**

# 二、抽象、模块化与信息隐藏，其实在解决同一个问题

这一部分先把几个容易混在一起的概念理清。

## 1. 模块并不等于一个类、一个文件或一个函数

Parnas 特别提醒：

> module 最好理解为一个 *work assignment unit*，而不是一个 subprogram。

这是全文一个非常重要、也很容易被忽视的地方。

一个模块真正表达的是：

> **关于系统的一组设计决策，应该由谁负责，其他部分需要知道多少。**

所以判断系统有没有良好的模块化，不能简单看：

* 文件是不是拆得足够小；
* 类是不是足够多；
* package 是不是足够整齐。

真正应该看的是：

> 修改一个设计决策时，究竟有多少地方必须跟着知道和修改。

## 2. 抽象：决定我们用什么概念理解系统

抽象解决的是“我们看到什么”。

例如调用：

`line.word(i, j)`

调用者面对的是“第 i 行第 j 个单词”。

它不需要面对：

* 字符如何压缩；
* 数据存在哪里；
* 有没有索引；
* 数据是否全部驻留内存。

这些实现细节从调用者的思维模型中消失了。

## 3. 信息隐藏：决定我们不应该知道什么

Parnas 的信息隐藏思想更进一步。

他提出：

> 每个模块都应该围绕一个重要的设计决策建立，并把这个设计决策隐藏起来。

所以模块边界实际上也是**知识边界**。

系统中的某个设计决策，只应该被一个尽可能小的区域知道。

从这个角度，可以给三者一个很清楚的关系：

> **抽象定义我们希望别人看到什么；
> 信息隐藏决定哪些知识不应该暴露；
> 模块化则把这些知识边界落实到系统结构中。**

# 三、真正重要的转变：从“按流程切分”到“按变化切分”

这一章可以成为全文最重要的例子。

Parnas 用 KWIC 系统给出了两种完全不同的模块化方案。

## 1. 最自然的设计：按照处理流程切

第一种方案几乎是所有程序员都会想到的：

Input
→ Circular Shift
→ Alphabetizer
→ Output

论文中的 Figure 1 本质上就是一张 flowchart。

这是一种非常自然的思考方式：

> 系统先做什么，然后做什么？

于是每一个 major step 成为一个模块。

问题在于，这些模块虽然在**执行流程上独立**，却共享大量关于实现的知识。

例如：

* 输入数据在内存里的格式；
* 字符如何编码；
* 行如何索引；
* Circular Shift 如何保存；
* Alphabetizer 的数据结构。

所以程序虽然被切成了几个盒子，设计知识仍然横穿整个系统。

## 2. Parnas 的设计：按照设计决策切

第二种设计包含：

* Line Storage
* Input
* Circular Shifter
* Alphabetizer
* Output

表面上名字变化并不大，真正变化的是模块定义。

例如 Line Storage 不再把内部数组交给别人。

其他模块只能通过它提供的操作去访问：

* 有多少行；
* 某一行有多少单词；
* 某个单词有多少字符；
* 某个字符是什么。

于是：

> **Line Storage 成为了“存储方式”这一设计决策的唯一知情者。**

这就是 information hiding。

# 四、判断模块设计好坏的最好办法：问“变化会传播多远？”

Parnas 接下来做了一件非常漂亮的事情。

他没有争论哪个结构“更优雅”，而是假设系统发生变化。

例如：

1. 输入格式发生变化；
2. 不再把所有行全部放进内存；
3. 不再采用四字符压缩；
4. Circular Shift 从保存索引改成直接保存结果；
5. Alphabetizer 从预先排序改成按需计算。

然后观察：

> 一个变化需要修改多少个模块？

在第一种设计中，“数据如何存储”几乎被所有模块知道。

所以一旦存储方式发生变化，修改会扩散到整个系统。

第二种设计里，存储方式只存在于 Line Storage 模块中。

因此变化可以被局限在一个模块里。

这里可以提炼出一个很适合全文反复使用的判断标准：

> **好的模块边界，是变化的防火墙。**

或者更进一步：

> **模块化的质量，可以通过 change propagation 来衡量。**

这样一来，“低耦合”这个有些抽象的词，就有了非常具体的含义：

> 一个设计决策发生变化时，有多少地方需要知道？

# 五、信息隐藏到底隐藏什么？

这一章可以专门把 information hiding 讲透。

很多人会把信息隐藏理解成：

* private 字段；
* getter/setter；
* implementation detail 不暴露。

Parnas 的意思远比这个宽。

他真正要求隐藏的是：

> **一个模块所掌握的设计知识。**

例如：

* 数据的表示方式；
* 数据存储策略；
* 算法选择；
* 排序究竟何时发生；
* 结果是预计算还是按需计算；
* interpreter 还是 compiler；
* 一个策略具体如何实现。

这些东西往往恰好也是：

> **最困难、最不确定、最可能变化的设计决策。**

因此 Parnas 在结论中给出了一个非常具体的设计方法：

> 先列出困难的设计决策，以及未来可能改变的设计决策，再围绕这些决策建立模块，使每个决策被隐藏在一个模块中。

这一点值得单独提炼成一句：

> **Parnas 实际上把“预测变化”放到了架构设计的中心位置。**

# 六、接口真正的作用：控制知识泄漏

这一章可以自然连接你想写的“接口隔离”。

Parnas 对 Circular Shifter 的反思非常值得展开。

原来的接口规定了 Circular Shift 的顺序。

后来他意识到：

调用者其实根本不需要知道这个顺序。

真正需要知道的只有：

* 所有 shift 都存在；
* 每个 shift 只出现一次；
* 可以找到它对应的原始 line。

一旦接口规定了顺序，调用者就可能开始依赖这个顺序。

以后如果想改变内部实现，这个原本没有必要存在的知识就变成了约束。

Parnas 甚至直接把这种设计称为：

> design error

因为接口暴露了**超过使用者实际需要的信息**。

这里非常适合提出：

> **接口设计的核心，不是“提供多少能力”，而是“暴露多少知识”。**

然后再连接现代软件设计里的 Interface Segregation Principle。

两者有明显的思想亲缘，但可以稍微区分：

* ISP 更强调：客户端不要依赖它不使用的方法；
* Parnas 的信息隐藏更广：客户端不要依赖它不需要知道的设计知识。

因此可以进一步得到一个更强的设计问题：

> **调用者完成自己的工作，最少需要知道什么？**

这个问题比“这个类应该提供哪些 API”更接近设计的本质。

# 七、不要把信息隐藏和分层混为一谈

这里进入你想讨论的“分层”。

这是 Parnas 论文后半段很重要、而且今天仍然经常被混淆的一点。

Parnas 明确区分：

* good decomposition
* hierarchical structure

层次结构建立在一种关系上：

> uses / depends upon

如果这种依赖形成 partial ordering，那么系统具有层次结构。

例如：

Symbol Table
↓
Line Storage
↓
Circular Shifter
↓
Alphabetizer / Output

低层可以独立存在，高层依赖低层。

这种结构带来两个额外收益：

第一，较高层可以依赖较低层提供的稳定服务，从而简化自身。

第二，可以把高层“剪掉”，保留下面部分形成另一个有用的系统。

Parnas 用了一个很形象的比喻：

> prune off the upper levels of the tree and start a new tree on the old trunk.

因此：

> **信息隐藏控制横向的知识传播；
> 层次结构控制纵向的依赖方向。**

两者都重要，但它们是独立的系统属性。

一个系统完全可能：

* 层次结构很清楚；
* 同时接口却泄漏大量内部设计决策。

这也是很多今天所谓“分层架构”依然难以维护的原因。

# 八、更深一层：好的模块设计其实是在延迟设计决策

这里可以利用论文的第二个 Markov Algorithm Translator 例子。

传统设计一开始就会决定：

* interpreter
* compiler

Parnas 的模块化方式把：

* Rule Storage
* Rule Interpretation
* Register Manipulation
* Sequencing

分开。

结果系统在相当晚的时候都可以不决定：

> 最终到底采用 interpreter 还是 compiler。

甚至可以在两者之间选择各种中间方案。

这说明信息隐藏还有一个非常深的价值：

> **它使尚未确定的设计决策保持局部化，从而推迟不可逆决策。**

这和今天架构设计中的：

* late binding；
* replaceable implementation；
* pluggable architecture；
* policy / mechanism separation；

都有很直接的联系。

可以把这一章的核心总结为：

> **优秀的架构并不会提前解决所有问题，它会让暂时不需要解决的问题继续保持可选择。**

# 九、AI 编程时代，模块化的重要性为什么反而上升了

这里再进入 AI，会比一开始就谈 AI 更有力量，因为前面已经建立了完整理论。

AI 最大的变化之一，是代码生产成本大幅下降。

过去写几千行代码很贵。

现在让 Agent 修改几十个文件、生成几千行代码并不困难。

因此一个新的风险出现了：

> **错误的结构也可以以前所未有的速度增长。**

如果模块边界不好，一个 Agent 为了完成一个需求，可能必须理解：

* 数据库 schema；
* controller；
* service；
* domain model；
* cache；
* event；
* UI；
* deployment configuration。

代码生成本身也许只需要几分钟，但它必须把大量跨模块知识放进上下文中。

这时 Parnas 的思想有了一个非常现代的解释：

> **模块边界同时也是 AI Agent 的 reasoning boundary 和 context boundary。**

好的信息隐藏意味着：

一个 Agent 修改某个模块时，只需要知道：

* 模块的契约；
* 输入输出；
* 少量依赖；

而不用知道整个系统的内部结构。

因此 Parnas 当年提出的三个收益，在 AI 时代可以重新理解：

**Independent Development**

从“不同程序员可以并行工作”，扩展成：

> 不同 Agent 可以在有限上下文中独立完成任务。

**Changeability**

从“修改代码影响更少模块”，扩展成：

> Agent 为一次修改需要读取、推理和重新生成的代码更少。

**Comprehensibility**

从“人可以一次理解一个模块”，扩展成：

> 人和 AI 都可以在有限认知窗口中理解一个局部系统。

这里需要明确说明：这是对 Parnas 思想的现代延伸，并非论文原文关于 AI 的结论。

# 十、AI 时代可能出现一种新的架构指标：认知局部性

最后可以从 Parnas 再往前走一步，提出自己的观点。

传统架构经常讨论：

* coupling；
* cohesion；
* performance；
* availability；
* scalability。

AI 编程时代还可以增加一个维度：

> **Cognitive Locality —— 完成一个修改，需要理解多少系统知识？**

可以提出几个很实际的问题：

* 改一个需求需要读取多少模块？
* 一个模块的实现变化会让多少接口失效？
* 调用者知道多少本来不需要知道的内部知识？
* Agent 是否必须不断跨越模块边界寻找上下文？
* 一个模块能否只凭自己的 contract 被独立修改？

这些问题其实都可以追溯到 Parnas 1971 年的核心思想。

# 结语：模块化管理的，是我们不得不知道的东西

可以最后回到全文最深的一层。

我们经常把模块化理解成一种代码组织技术：

文件怎么拆，类怎么写，package 怎么组织。

Parnas 提出的视角要深得多。

系统真正难以管理的原因，是随着规模增长，越来越多设计决策开始互相泄漏。

一个模块知道另一个模块如何存储数据；

一个调用者知道另一个组件何时排序；

一个服务知道数据库内部表结构；

最后每一个局部变化都必须重新理解整个系统。

信息隐藏试图建立一道边界：

> **让一个设计决策，只存在于真正需要知道它的地方。**

五十多年以后，程序员开始与能够快速生成海量代码的 AI 一起工作，这个原则反而显得更加重要。

因为代码可以生成得越来越快，

而一个复杂系统中真正稀缺的资源，依然是：

> **我们能够可靠理解和推理的范围。**
