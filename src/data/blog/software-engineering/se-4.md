软件工程讨论的是一个大规模团队如何协作来完成一个大规模软件项目的问题。

如果是团队规模较小，如三五个成员或者单兵作战；或者项目规模较小，如一个简单的工具软件或者一个小型网站，那么软件工程的很多问题并不会显现。

软件工程采用的流程和工具也与规模强相关。

很多流程和工具我们每天都在使用，习以为常就认为理所当然。其实，流程和工具都是经过发明、试错、反馈、演化逐渐变成今天的模样。

每一阶段的变化都是为了解决特定问题。当规模的增长成为问题根源时，流程和工具也要适时调整。

顺便提及，以问题思维看待技术，梳理技术发展的脉络，做到知其所以然，有利于加深对概念和原理的理解，从而提出自己的方案和见解。

这篇文章以版本控制和Build工具为例，具体谈谈这个话题。

## 理解版本控制系统（VCS）
在多人协作开发的需求下，为什么需要版本控制系统（Version Control System）？本质上，我们想要的不是版本，而是某一时刻某个文件的具体内容。

版本控制系统（VCS）可以理解为一个扩展的文件系统[1]。

一个文件系统本质上是从文件名到文件内容的映射 M：

> File System: M (name) => Contents

VCS 在此基础之上引入了时间的概念，每个文件改动都有对应的时间戳。有了时间，就会有顺序，有基准，有协作，也有冲突。因此这个映射变为：

> VCS: M (name, time) => Contents

有时时间也不能唯一去定文件的状态，因为分工协作还可能出现并行修改的行为，即一个文件在同一时间可以有两种状态，这就是分支（branch）。因此，映射进一步变为：

> VCS: M (name, time, branch) => Contents

也就是说在版本控制系统中，一个文件的内容与它的名称、修改时间和所在分支同时决定。

这就是为什么有了 VCS，团队和项目就可以伸缩和规模化。当大量人员参与进来时，以上三个因素都会同时剧烈变化，想要得到一份文件的具体内容，就需要一种确定的机制来保证。

最终上线的代码版本只有一个，通常就是主干分支（trunk 或 main），其他的开发分支应该合入主分支。分支的存在是必要的，合入也是必要的，冲突就在所难免。

降低解决冲突的难度，应当着眼于使冲突的改动最小化，方法就是增加合入的频率。

因此，尽量不要使用长期存在的 dev 或 feature 分支，而是直接基于主分支开发。每天的改动合入主分支，依赖充分的自动化测试和继续集成（CI）工具链保证主分支代码的正确性。

很多团队发现，自己的开发分支在积累了大量 commit 之后，很难合入主分支，冲突不断，也无法保证正确性，需要额外的测试。

但他们仍然着手解决“症状”，而不是根因。症状是开发分支合入困难，自然的想法就是学习合入的技巧、降低合入的风险等，但这只是头痛医头，脚痛医脚。

根本的解决方案是要减少开发分支的使用，增加合入次数，并建立完善的测试和集成系统。

## 理解 Build 工具

作为开发者，我们对各类 Build 工具并不陌生，稍微有点经验的工程师应该至少接触过一到两种工具，比如 Make、Maven、Bazel、Grunt 等等。

如果你已经认同，Build 工具是开发流程中必要的工具，接下来就是如何选择的问题。选择合适的 Build 工具需要对候选工具的设计思路进行分析。

一般而言，Build 系统要同时兼顾两个特性[1]：

- 快速：开发者期望很快得到Build 结果，以便获得已有代码的快速反馈。CI 系统也希望快速得到 Build 结果，以便尽早发现问题，节省资源。

- 正确：正确是指，在输入不变的情况下，任意开发者在任意机器上运行 Build 都能得到相同的结果。

仔细考察第一个目标：要想实现「快」，一个直观的思路是，只 Build 需要的、最小范围的目标（target）。这就需要追踪所有 Build 的依赖和目标，保证每次 Build 是增量的。

对于第二个目标「正确」，我们再次强调它的含义：

> 给定同样的源文件和其他输入（如配置文件），任何开发者在任何机器上，每次运行 Build 都能得到相同结果。

如果 Build 工具或系统设计得不完善，可能出现「快速但不正确」的情况。

例如，开发者改动了项目中的某个配置文件，但是 Build 工具的配置不支持该文件的声明，Build 系统就无法发现这个改动，因此重新 Build 什么也没有做。

这是一次很快的 build，但是并不正确。因为如果代码提交后，由另一个工程师拉取并从头运行 Build，就会得到不一样的结果。

对于简单项目而言，快速且正确的Build似乎也不难实现，只需要注意实现的性能，管理好依赖和目标的追踪。

不过还是回到那个软件工程永恒的话题——可规模化（Scalable）：当项目日渐复杂，Build 工具是否还可以在可接受的时间内完成正确的 Build 任务？

对于规模化的项目，每个开发者需要Build的目标会显著变多，同时又需要多个开发者的协作，此时快速和正确的必要性体现的更为明显。

具体地，下面几个问题自然产生：

1. Build 是否可以并发或者并行的进行？（快速）

2. Build 的结果是否可以被自己或者他人重用？（快速、正确）

3. Build 的结果是否可以在其他机器上复现？（正确）

下面我们以 Google 开源的 Build 工具 Bazel [2]为例，看看如何解决这些问题。重点在于工具的设计思想，而不是使用方法。

首先，要实现多个Build 目标（如编译）的并发，在性能方面，对于现代的服务器或工作站来说不是问题。我们需要关注的是，不同 Build 目标之间的依赖关系。

如何描述和处理这种依赖关系，又涉及两种Build工具的设计思路：基于任务（Task-based）和基于构件（Artifact-based）。

常见的基于任务的工具有Java技术栈的Maven，以及JavaScript技术栈的Grunt.js等等。其特点是支持自定义构建脚本，可以提供给开发者强大的能力，但同时也引入了复杂性。

工具无法预知开发者的脚本的具体行为，在优化和调度任务的执行时，只能采取相对保守的策略。同时，任务脚本变得复杂和难以理解的可能性也更高，因为脚本功能更为强大嘛。

举个例子，对于并发执行 Build 任务的场景，task A 依赖 task B 和 C，B 和 C 之间没有声明依赖关系。

按理说，工具可以调度 B 和 C 并发执行以提高 Build 效率。然而，工具无法预知任务 B 和 C 在实现层面是否有依赖，例如是否会访问同一份文件记录状态。

因此，为了保证正确性，保守的策略依然是顺序执行。

这也是工具设计的一个权衡：提供过多灵活性，就引入未知的复杂性，为了兼容而放弃优化；只提供基本的功能，能从容和充分地优化框架的代码，获得最优的性能，但却丧失了实现的灵活性。

事实上，对于 build 系统来说，开发者只需要指定 Build 什么（what），由工具来决定如何（how） Build。从具体任务的角度说，这个具体有哪些 Build 任务应该由工具决定。

这就是基于构件 Build 工具的设计思路。

这有点像命令式 （imperative）编程语言和声明式（declarative）编程语言的区别。前者不仅描述了要做什么，还通过一行行语句说明怎么做；后者则只是声明要达到的目的，但将实现细节留给编译器。

Bazel 就是一种典型的基于构建的 Build工具，由 Google 内部构建工具 Blaze 开源演化而来。

Bazel 支持的 Build 目标（target）类型是预定义的，这就方便build工具去内部优化build过程。

比如 java_library，Bazel 知道使用 java 编译器去编译指定的源文件和依赖，那么很多同样的 target 就可以并行执行。

同时，函数式的思想也保证，同样的输入一定会得到同样的输出：源文件和编译器到输出的映射 f：

> build_output = f(source_files, compiler, compiler_options)    

因此，只要检查源文件是否改动，就可以知道输出结果是否是最新的，进而决定哪些需要重新 Build，哪些只需要维持原状。

注意这里的编译器，Bazel 认为编译工具也是 target 的一种依赖，可以在 workspace 全局配置。如果你配置了编译器的属性，一旦发生变更，相关的 Build target 都需要重新来。

同时，Bazel 还支持 toolchain [3]机制，让 build 具备可移植性，而不依赖于本地设备的特征（如环境变量、平台类型等）：

> A toolchain contains a set of tools and other properties defining how a type of target is built on a particular platform. 

这就是 Build 的正确性的体现。

当项目足够大，需要 Build 的目标足够多时，基于缓存的单机 Build 也不能满足快速 Build 的要求。

因此，Bazel 可以实现分布式 Build：可将 Build 目标拆分成一系列的 actions，提交到 Build 的 master 节点，由 master 节点调度并分配到多个 worker 节点上执行具体的 Build。

同时，Build 的结果可以在 worker 之间共享，也可以缓存下来。当每个 worker 的 Build 完成后，作为整体的输出结果返回给请求方（如开发者或者 CI 工具）。

这里面复杂性体现在，用户、master 节点和多个 worker 几点之间的通信和数据同步如何正确实现，保证最终 Build 输出的正确性。可以想象，基于 task 的 build 工具是很难实现类似功能的。

总之，Bazel 的设计思路都是围绕我们最初提到的两个目标：快速和正确。

这一节不是在推荐使用 Bazel 工具，而是希望通过分析其设计，帮助大家理解 Build 工具的设计原则，从而在选择和使用时不盲从，做到心中有数。

## 结语
从版本控制和 Build 工具的讨论可以看出，软件工程中的流程和工具并不是凭空产生的，而是为了解决特定的问题，而规模化始终是绕不开的问题。
